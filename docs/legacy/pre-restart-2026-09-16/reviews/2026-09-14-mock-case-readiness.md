# Mock Case 生成前置条件报告：缺少的能力、约束实现与信息

日期：2026-09-14。范围：V1 已结案 mock Case 的构造与验收，不扩展到完整检索 Benchmark。

本报告是当前代码和资料的审查快照。它区分已经冻结的规则、尚未实现的检查，以及仍需选择的生成配置；不新增业务规则或硬性阈值。

依据：[冻结结构](../data/CaseTrace_Data_Structure_V2_No_Scenario.md)、[CR](../data/CaseTrace_Case_Constraint_Rules_Frozen.md)、[GR](../data/CaseTrace_Case_Generation_Rules_V1.md)、[审计确认](../data/CaseTrace_Structure_Logic_Audit_Confirmation.md)、[实现清单](../data/CaseTrace_Validator_Implementation_Plan.md) 和 [主数据 Excel](../../../../data/reference/封装异常_failure_modes_db_structured_v5_engineering_audited-2.xlsx)。

## 1. 结论

基础资料已经具备，模型和部分确定性校验已经实现。当前可以人工构造少量开发样例并逐条审查；还不能自动批量生成并证明这些 Case 符合全部 CR、GR 和语义要求。

“缺少部分”主要分成三类：

| 类别 | 当前情况 | 应补充在哪里 |
|---|---|---|
| 规则已有，代码未实现 | 主数据导入、部分 GR、语义审查和生成流程尚未接入 | 运行代码及对应测试／审查流程 |
| 参数口径尚未确定 | “少量”“通常半年内”等尚无完整可执行配置 | 生成配置；若要改变冻结规则，更新原权威文档 |
| 每次生成才会产生的信息 | 实际批号、选择的候选、调查事实和结案判定等未形成生成上下文 | 生成过程中保留的上下文及运行记录 |

主要问题不在于继续增加 Case 字段。冻结结构已经给出调查文本与实际生产事实的存放位置。

## 2. 主数据已经有什么

本轮实际读取 Excel，确认有 12 张 Sheet、498 条有效记录。其中包括：

| 资料 | 已有内容 | 对生成的作用 |
|---|---|---|
| 客户与产品 | 5 个客户、18 个产品、18 条固定客户归属 | 按固定归属生成，保证同 Case 的产品属于同一客户 |
| 产品路线 | 3 条路线及产品族、工序相关资料 | 支持路线适配与背景选择 |
| 固定 BOM | 77 条 Product—Material 关系 | 确定各产品实际配置的材料 |
| Failure Mode | 37 条记录及原因、措施候选 | 为异常、原因和措施选择提供来源 |
| 设备 | 62 条设备记录及工序引用 | 为实际设备调查事实提供合法候选 |
| 材料与工序知识 | 材料及其路线、工序关联 | 支持材料适用性检查和候选选择 |

本轮结构核对中，未发现所检查的实体 ID、客户覆盖、产品／设备／材料引用、BOM 类别及路线适配问题。此结论只覆盖当时检查的项目，不等于建立了完整的导入校验器或证明所有文本候选在任意组合下都合理。

一个具体边界是 `00027 / embedded component short`：其 `detection_methods` 和 `screening_methods` 为空，且涉及内部 SMT 元件。检测候选为空本身不是 Case 硬性非法条件；冻结结构同时明确当前 BOM 未配置可选 SMT 元件，因此不能仅因为该异常适用于 SUBSTRATE_FC 就直接生成对应的实际使用事实。

这说明生成器必须区分“知识库中存在”与“当前产品可以生成”。

## 3. 缺少的运行能力

### 3.1 主数据读取和导入校验

当前 `validate_relations()` 接收人工构造的三个映射，尚未从 Excel 自动构建它们。

需要补充的工作包括：

- 读取各 Sheet，并在构造字典前检查重复 ID 和重复关系，避免覆盖后丢失错误证据；
- 保留 ID 的文本形式，尤其是 Failure Mode ID 的前导零；
- 拆分路线集合与候选文本，并保留其源记录；
- 校验客户／产品覆盖、产品族与路线引用、BOM 唯一性和完整性；
- 按结构文档检查路线、工序、设备和材料之间的主数据关系。

现有 `check_reference_maps()` 只检查接口形状及两份 Product 映射的覆盖一致性，不能替代上述工作。

### 3.2 可复现的结构化生成

当前没有 generator。需要由 Python 按 GR 先决定产品、批号、时间、异常、数量、Evidence 类型与 relevance，以及原因／措施候选和实际生产事实。

还需要记录本次使用的配置、随机种子和主数据／规则版本，以便复查或重新生成结构化部分。对不符合路线、BOM 或组合逻辑的候选，应按已有规则筛选或重选；不因知识库提供了某个值就直接采样。

这些属于生成流程的职责，不应靠在最终文本中搜索关键词来补救。

### 3.3 文本组织、审查与验收汇总

尚无按照既定事实组织文本的流程，也没有把确定性错误、语义审查结果和待审查事项汇总成一次完整验收的实现。

确定性检查通过后，仍需核对异常描述、调查结果、原因、措施和处置是否准确表达预先确定的事实。人工审查可以用于早期少量样例；使用 LLM 改写时，不能让它自行决定 Canonical Truth 或扩展候选概念。

“通过”“失败”“待审查”的表达方式是后续接口设计问题。本报告不规定新的返回类型，也不把尚未审查伪装为通过。

## 4. 已有约束中，哪些还没有完整执行

### 4.1 CR 和结构要求

| 规则来源 | 当前覆盖 | 缺少什么 |
|---|---|---|
| 结构 §1、§5 | 已检查 Case 使用的映射形状、引用和路线适配 | 完整主数据导入检查；将来落库时的约束与事务实现 |
| CR-13 | 异常描述已有非空检查 | 描述与 Detail 明确事实的一致性审查 |
| CR-26 | 数量已检查为正整数 | 文本与上下文中的数量是否采用处置范围口径 |
| CR-27～29 | 处置、原因和措施已有非空检查 | 是否为最终处置、明确结案结论和具体措施；NDF 是否仍有合格措施 |
| CR-34、43 | Other 的条件必填已检查 | 名称是否具体、说明是否真正解释分组类型 |
| CR-35 | 具备 Evidence 结构和 relevance 标签校验 | 明确的 confirmed／NDF 判定；对 confirmed Case 检查 related Evidence，并审查支持关系 |
| CR-36 | 尚无语义检查 | related Evidence 的结果是否反驳其支持的原因 |
| CR-37 | 尚无适用性复核提示流程 | 根据上下文提示缺少适用调查项；保持 Soft，不作为硬错误 |
| CR-44 | 分组类型、成员引用和数量已检查 | repeat_case 是否存在明确确认的复发关系 |
| 结构 §6 / B07 | Evidence 可以承载事实文本 | 实际设备、参数调整、材料料号／批号和 wafer lot 的上下文核对与表达审查 |

不能根据 `root_cause` 中是否出现“NDF”几个字符可靠判定结案类型，也不能把 `relevance="related"` 当成证据充分性的证明。

### 4.2 GR 生成要求

| 规则 | 当前覆盖 | 尚缺部分 |
|---|---|---|
| GR-01 | 每 Case Detail 数量的下限由 CR 检查，上限由 GR 检查 | 单／多产品的实际采样，以及固定主数据的接入 |
| GR-02 | 异常引用、路线适配、至少一个异常和最多两个生成异常 | 单／双异常采样与实际比例统计 |
| GR-03 | Product 与异常路线适配只是其中一部分 | 双异常逻辑、原因／措施与路线及 BOM 一致性审查 |
| GR-04 | Dataset 复用批号种类数量检查；固定属性由 CR 检查 | 按该规则安排批号的生成流程 |
| GR-05 | 日期类型和发现时间不早于投批时间 | 时间采样配置及间隔分布报告 |
| GR-06 | 正整数与每 Detail 数量上限已检查 | 按此范围生成数量；继续保持同批事件数量不能当作去重实物量累加的口径 |
| GR-07 | Evidence 最少数量、字段、枚举和 Other 必填 | 调查项与事实的选择、B07 事实覆盖及语义审查 |
| GR-08、09 | 原因／措施文本非空 | 候选来源保留、来源核查及改写后的概念一致性审查 |
| GR-10 | 各实体可以承载最终记录 | Python 先定事实、LLM 组织文本的流程，以及来源／事实／审查信息的保留 |

这些主要是规则实现缺口，不是需要重新发明的业务约束。

## 5. 哪些信息需要在生成过程中补齐

下面的信息通常来自某次生成的选择或人工确认，并不意味着要给 Case 增加永久字段。具体上下文结构尚未实现。

| 信息 | 用途 | 来源或形成方式 |
|---|---|---|
| 本次选用的原因／措施候选及其来源记录 | 核对 GR-08、09，检查改写有没有新增概念 | 生成器保留主数据来源及选择结果 |
| confirmed／NDF 判定 | 决定 CR-35 的适用性 | 生成上下文或人工审查；不能仅搜索自由文本 |
| 设备、参数调整、material_id、material lot、wafer lot | 核对 B07 与 GR-07，审查 Evidence.result | Python 先确定；设备和材料引用受主数据及事实背景约束 |
| 原因与调查项的支持关系、复发理由 | 审查 CR-35、36、44 | 既定事实与人工／语义审查结果 |
| 规则版本、主数据版本、随机种子和生成配置 | 复现结构化记录与定位生成问题 | 每次生成的运行记录 |
| 待审查项及审查结论 | 区分确定性通过和完整验收 | 校验／审查流程汇总 |

材料批号、wafer lot 和本次参数调整不是主数据 Excel 必须预先列完的静态值。它们应在生成过程中确定，并按冻结结构写入对应 Evidence.result。

## 6. 哪些参数或口径仍未确定

| 项目 | 冻结资料已经说明什么 | 尚需选择或澄清什么 |
|---|---|---|
| 多 Product | 默认单 Product，少量多 Product，且同 Case 同客户 | 具体采样配置；没有可直接用作硬拒绝条件的比例 |
| 单／双异常 | 约 90%／10% | 如何采样和展示实际比例；没有冻结的验收容差 |
| 时间间隔 | 通常半年内，少量超过半年 | 日期范围、采样配置及统计口径；不能自行把超过半年判为非法 |
| 本次生成规模 | 已约束每 Case Detail 数和 Dataset 复用批号数 | 本次要生成多少 Case；配置须能够满足已有规则 |

这些参数并不阻止开始少量人工样例。开始可复现批量生成前，应明确本次配置并保存；若要把配置升级为业务硬约束，应修改对应的权威来源。

未提供的质量标准、车规属性和尺寸，不应补造为已知事实。当前也不需要新增 Scenario 实体、compatibility 表、ProductionLot 主表或 lot_total_qty 来解决上述缺口。

## 7. 建议的最小补齐顺序

以下是实施建议，不是本次已经完成的功能：

1. **接入主数据。** 能读取并校验现有 Excel，形成可追溯的映射和候选数据。
2. **构造少量结构化开发样例。** 使用固定种子和明确配置，安排产品、批号、日期、异常、数量与调查事实，通过现有确定性 CR／GR 检查。
3. **保留上下文并审查文本。** 核对候选来源、confirmed／NDF 判定、原因—证据—措施逻辑和 B07 表达，明确待审查项。
4. **在样例可信后扩展批量生成。** 输出分布统计和生成记录，处理不合格组合的重选与复核。

数据库可以后续接入，不是少量内存样例的先决条件。Current Incident 的时间切片、Development／Locked Test 划分及检索 Ground Truth 属于后续数据与评估工作；生成已结案 Case 不等于已完成这些任务。
